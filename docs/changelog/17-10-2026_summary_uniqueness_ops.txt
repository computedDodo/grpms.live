1. Executive Summary

This change addressed two related operational concerns in GRPMS:

1. Enforcing school-code uniqueness consistently at the application and database levels.
2. Aligning the PythonAnywhere production database with the development database so that the live demo environment contains the latest demonstration data.

The school-code work introduced application-level duplicate validation, database-level uniqueness enforcement, a dedicated database migration, tests, and technical documentation.

The production deployment was updated from the previous application revision to the new code on GitHub's "main" branch. The database migration was subsequently verified at revision "0004_enforce_school_code_uniqueness".

A separate database restoration was then undertaken because the development environment contained additional second-term demonstration activity that was missing from production.

The original database export was not suitable for direct import into the production MySQL server because it contained MariaDB-specific collation information. A new, MySQL-compatible export was generated and uploaded.

The import processed substantial amounts of data but reported a character-set restoration error. Subsequent record-count comparisons showed matching counts for nine selected tables. However, the complete database and application have not yet been verified end to end.

Current conclusion: The code deployment and migration are verified at the recorded revision. The database restoration appears substantially successful, but the character-set error and remaining verification items must be recorded rather than treated as resolved.

2. Background and Original Problem

GRPMS supports multiple schools within the same platform. Each school has a school code used for identification and related school-specific operations.

The uniqueness requirement is important because duplicate school codes could cause ambiguity in school identification and related workflows.

The original implementation review identified two complementary requirements:

- Application-level validation should reject duplicate school codes and handle database integrity errors safely.
- The database must independently enforce uniqueness so that concurrent requests or alternate write paths cannot bypass application validation.

Application validation alone is insufficient as a concurrency safeguard. Two requests can both pass an initial duplicate check before either inserts its record. A database unique constraint provides the final integrity guarantee.

The production migration also needed to preserve existing school codes. Automatically rewriting existing codes during a migration could create unexpected changes to established identifiers and potentially affect related workflows.

Environment context

At the time of implementation, development and production contained the same single demonstration school:

- School: Grade6ix Demo Academy
- School code: "DMA"

No real schools had been onboarded. This was an explicit consideration in the decision to replace the production demonstration database with the development demonstration database rather than merge the two.

The replacement was intended to reproduce the development demonstration state, including the second-term activity.

3. Proposal and Technical Decision

The original proposal called for a two-layer uniqueness safeguard.

3.1 Application-layer protection

The application should:

- Normalize school codes consistently before comparison.
- Reject a school code that conflicts with an existing school code.
- Return an appropriate validation response to the user.
- Handle database integrity errors safely.
- Roll back a failed database transaction rather than leave the session in an invalid state.

3.2 Database-layer protection

The database should enforce a unique constraint named:

"uq_schools_code"

This constraint prevents duplicate non-null school codes from being stored, including when application-level checks are bypassed or concurrent operations occur.

The database migration was assigned the revision:

"0004_enforce_school_code_uniqueness"

Its recorded predecessor is:

"2ef9e254bb24"

3.3 Migration safety decision

An important issue emerged during the implementation review.

An earlier migration approach could normalize or rewrite existing school codes automatically. That approach was reconsidered because the migration should not silently change existing identifiers.

The safer implementation direction was to validate existing data, detect conflicts requiring attention, and enforce the constraint without automatically rewriting existing school codes.

This preserves existing identifiers and makes any necessary data correction an explicit decision rather than an incidental effect of a schema migration.

3.4 Backup requirement

Before proceeding, a database backup was required.

The development backup was created before implementation using the following command:

"mariadb-dump -u root -p grpms_dev > beta_backup_before_school_code_uniqueness.sql"

The original local backup was reported to be approximately 245 KB, with a recorded dump completion time of 16 October 2026 at 23:25:53.

This backup belongs to the school-code uniqueness implementation stage. A separate, later export was created specifically for production database restoration.

7. Development-to-Production Database Restoration

7.1 Objective

Following the application deployment, development and production still needed to be aligned at the data level.

The development database, "grpms_dev", contained the fuller demonstration dataset, including second-term activity that was missing from the production demo.

Because no real schools had been onboarded, the agreed approach was to replace the production demonstration dataset with the development demonstration dataset, rather than merge records.

7.2 Original export incompatibility

The first export was named:

"beta_backup_before_school_code_uniqueness.sql"

It was a MariaDB dump and contained schema definitions and data statements, including "DROP TABLE", "CREATE TABLE", and "INSERT INTO".

Two compatibility issues were identified:

MariaDB-specific collation

The original dump included:

"utf8mb3_uca1400_ai_ci"

That collation was incompatible with the target production MySQL 8.0.42 environment.

Alembic migration revision

The original dump also contained the older migration revision:

"2ef9e254bb24"

Its "alembic_version.version_num" column was defined as "VARCHAR(32)", which was too short for the newer revision name "0004_enforce_school_code_uniqueness".

Consequently, importing the original dump unchanged would have risked both a collation error and an incorrect migration state.

7.3 MySQL-compatible export

A new export was generated from the development database using:

"mariadb-dump -u root -p --skip-create-options grpms_dev > beta_backup_mysql_compatible.sql"

The resulting file was approximately 244 KB.

The checks performed on the new export established that:

- A search for "uca1400" returned no matching lines.
- The school and score data were present.
- The "alembic_version.version_num" column was defined as "VARCHAR(64)".
- The recorded migration revision was "0004_enforce_school_code_uniqueness".

The file was then uploaded to:

"/home/CyberDodoo/beta_backup_mysql_compatible.sql"

The uploaded file was reported as approximately 244 KB.

7.4 Import execution

The production MySQL shell was opened against "CyberDodoo$grpms", and the uploaded export was executed using:

"source /home/CyberDodoo/beta_backup_mysql_compatible.sql"

The shell reported many successful statements, including table operations and inserts.

However, the import ended with the following error:

"ERROR 1231 (42000): Variable 'character_set_client' can't be set to the value of 'NULL'"

It also reported:

"ERROR: No query specified"

The import appeared to continue processing statements around the error. Because the MySQL client can continue after an individual statement fails, the error cannot be dismissed solely because later statements succeeded.

Important: The database had already been modified by the import. The correct next step was to inspect the resulting database, not to rerun the export immediately. The dump contains "DROP TABLE" statements and therefore can drop and recreate tables on a subsequent execution.
